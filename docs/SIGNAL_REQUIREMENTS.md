# Signal — Product Requirements Document

## 1. Overview

### 1.1 Product Name

**Signal**

### 1.2 Concept

Signal analyzes content and detects signals that indicate whether the content may have been generated by AI.

Signal should not simply claim that content is "AI-generated" or "human-generated." Instead, it should provide an AI-likelihood score, confidence level, and the signals that contributed to the result.

> **Signal — Detect the signals of AI-generated content.**

### 1.3 Background

Generative AI has made it increasingly difficult to distinguish human-created content from AI-generated content.

Existing AI-content detectors often have several limitations:

- They provide a score without explaining why.
- They imply certainty where certainty is not technically possible.
- They are primarily exposed through web UIs.
- They are difficult to integrate into developer workflows and other systems.

Signal will initially be delivered as a developer-focused CLI, followed by an API. The API will become the foundation for MCP, browser extensions, and other integrations.

---

## 2. Product Principles

### 2.1 Analyze Rather Than Assert

Signal must not treat AI-generation detection as absolute proof.

Results should express:

- AI-generation likelihood
- Classification
- Confidence
- Signals contributing to the result

For example:

```text
AI likelihood: 87%
Confidence: High

Signals:
- Repetitive sentence structure
- Consistent sentence length
- AI-like phrase patterns
- Low stylistic variation
```

### 2.2 Explain the Result

Signal's value should not be limited to a single score.

The system should explain **why** a result was produced by exposing the signals that contributed to the analysis.

### 2.3 API-Centered Architecture

The analysis engine must be independent of its user interfaces.

The planned architecture is:

```text
                    ┌──────────────┐
                    │Signal Engine │
                    └──────┬───────┘
                           │
                 ┌─────────┴─────────┐
                 │                   │
             Signal CLI          Signal API
                                     │
                         ┌───────────┴───────────┐
                         │                       │
                    MCP Server            Browser Extension
```

CLI and API should use the same analysis engine so that detection logic does not diverge.

## 3. Target Users

### 3.1 Initial Users

The primary audience is developers, including:

- Developers who want to inspect AI-generated text or code.
- Developers who want to inspect content generated by AI agents.
- Developers who want to analyze content from GitHub.
- Developers who want to run AI-content checks in CI/CD.

### 3.2 Future Users

Once the API is available, Signal should support systems such as:

- AI agents
- MCP clients
- Browser extensions
- CMS platforms
- Education services
- Content management systems
- Enterprise content-management tools
- Systems enforcing AI-use policies

## 4. MVP Scope

The first MVP focuses on **AI-generation likelihood analysis for text content through a CLI**.

### Inputs

The MVP should support:

- Standard input
- Text files
- Markdown files

URL input may be added after the initial MVP.

### Outputs

The MVP should provide:

- AI-generation likelihood score
- Classification
- Confidence
- Signals contributing to the result
- Input character count
- Input word count
- JSON output

## 5. CLI Requirements

### 5.1 Basic Command

```bash
signal <input>
```

Example:

```bash
signal article.md
```

Standard input should also be supported:

```bash
cat article.md | signal
```

URL support is planned for a later phase:

```bash
signal https://example.com/article
```

### 5.2 Human-Readable Output

The default output should be designed for developers.

Example:

```text
Signal

AI likelihood    87%
Confidence       High

Signals
  ✓ Repetitive sentence structure
  ✓ Consistent sentence length
  ✓ AI-like phrase patterns
  ✓ Low stylistic variation

Analyzed
  4,821 characters
  823 words
```

### 5.3 JSON Output

Machine-readable JSON must be available.

```bash
signal article.md --json
```

Example:

```json
{
  "score": 0.87,
  "confidence": "high",
  "classification": "likely_ai_generated",
  "signals": [
    {
      "type": "repetitive_structure",
      "score": 0.82
    },
    {
      "type": "phrase_pattern",
      "score": 0.76
    }
  ],
  "input": {
    "characters": 4821,
    "words": 823
  }
}
```

The CLI JSON format should be compatible with the future API response format wherever practical.

### 5.4 Exit Codes

The CLI should support CI/CD use cases.

Initial exit-code proposal:

```text
0 = Analysis completed successfully
1 = AI-generation likelihood is at or above the configured threshold
2 = Invalid input
3 = Analysis error
```

The threshold should be configurable:

```bash
signal article.md --threshold 0.8
```

## 6. Analysis Engine

### 6.1 Analysis Granularity

The engine should be designed to support document-level analysis and future fine-grained analysis.

Conceptually:

```text
Document
 ├── Paragraph
 │    ├── Sentence
 │    └── Sentence
 └── Paragraph
```

This enables future functionality such as identifying AI-like sections within an otherwise human-written document.

### 6.2 Signals

The analysis engine should detect multiple independent characteristics.

Potential signals include:

- Sentence structure
- Sentence-length variation
- Vocabulary diversity
- Repeated expressions
- Text structure
- Phrase patterns
- Unusual consistency
- AI-associated language patterns

Each signal should be implemented as an independent analyzer where practical.

Example:

```text
Analyzer
 ├── StructureAnalyzer
 ├── VocabularyAnalyzer
 ├── PhraseAnalyzer
 ├── StyleAnalyzer
 └── ...
```

The architecture should make it easy to add new analyzers.

### 6.3 Overall Score

The overall AI likelihood should be derived from multiple signals:

```text
AI likelihood = f(signal1, signal2, signal3, ...)
```

The exact scoring algorithm should be determined through experimentation and evaluation.

---

## 7. Classification

Signal should avoid a simple binary classification.

The initial classification set should be:

```text
likely_human
possibly_human
uncertain
possibly_ai_generated
likely_ai_generated
```

The result should also include:

```text
score
confidence
```

Score and confidence must be independent concepts.

For example:

```text
AI likelihood: 85%
Confidence: Low
```

is valid when the observed signals indicate AI-like characteristics but the available input is insufficient for a confident conclusion.

---

## 8. Input Constraints

Very short content may produce unreliable results.

The system should adjust confidence based on input size.

Initial thresholds are examples only and must be validated experimentally:

```text
< 100 words
  → insufficient_data

100–500 words
  → low confidence

500–1,000 words
  → medium confidence

> 1,000 words
  → normal analysis
```

Final thresholds must be determined using evaluation data.

---

## 9. API

The second phase is to expose Signal as an API.

### 9.1 Endpoint

Initial endpoint:

```http
POST /v1/analyze
```

Request:

```json
{
  "content": "..."
}
```

Response:

```json
{
  "score": 0.87,
  "confidence": "high",
  "classification": "likely_ai_generated",
  "signals": []
}
```

### 9.2 API Design

The API is not a separate analysis implementation.

It is another interface to the same analysis engine used by the CLI.

```text
                 ┌───────────────┐
                 │ Analysis Core │
                 └───────┬───────┘
                         │
              ┌──────────┴──────────┐
              │                     │
             CLI                   API
```

### 9.3 Authentication

API-key authentication should be the initial mechanism.

The architecture should allow future support for:

- API keys
- OAuth
- Service accounts

### 9.4 API Controls

The API should support management of:

- Request limits
- Input-size limits
- Usage
- Rate limits
- API-key-specific usage

After the API is available, provide an MCP server that uses the Signal API.

The goal is to allow AI agents to analyze content through Signal.

Initial tool:

```text

```

Input:

```json
{
  "content": "..."
}
```

Output:

```json
{
  "classification": "likely_ai_generated",
  "score": 0.87,
  "confidence": "high",
  "signals": []
}
```

Conceptual architecture:

```text
AI Agent
    │
    │ analyze content
    ▼

    │
    ▼
Signal API
    │
    ▼
Analysis Engine
```


## 14. Non-Functional Requirements

### 14.1 Reproducibility

The same input should produce the same result whenever practical.

If external AI models are used, the result should be traceable to the model and model version used.

### 14.2 Performance

The initial goal is to analyze typical text within a few seconds through the CLI.

### 14.3 Privacy

Content submitted to Signal may contain confidential information.

Therefore:

- Content should not be persistently stored by default.
- Content should not be written to logs.
- API data-retention policies must be explicit.
- Users must be able to understand how submitted content is handled.

### 14.4 Observability

The API should record operational metadata such as:

- Request ID
- Processing time
- Input size
- Analysis-engine version
- Model/algorithm version
- Errors

Content itself should not be logged by default.

---

## 15. Accuracy Evaluation

Accuracy evaluation is a core requirement.

Signal should maintain an evaluation dataset containing:

```text
Human-written
AI-generated
Human-edited AI-generated
AI-edited human-written
Mixed content
```

Human-edited AI-generated content is particularly important because real-world AI-generated content is often modified by humans.

Evaluation should consider:

- Accuracy
- Precision
- Recall
- F1 score
- False-positive rate
- False-negative rate

The evaluation dataset and evaluation process should be versioned so that changes to the analysis engine can be compared over time.

---

## 16. Important Limitations

Signal does not provide absolute proof that content was or was not generated by AI.

All CLI, API, and UI surfaces should clearly communicate that the result is a probabilistic analysis.

Recommended wording:

> **Signal does not prove that content was generated by AI. Results are probabilistic estimates based on detected signals.**

Signal should explicitly discourage using its result as the sole basis for high-impact decisions in areas such as:

- Education
- Hiring
- Human resources
- Legal decisions

## 18. MVP Success Criteria

### Technical

A text file can be analyzed within a few seconds.

### User Experience

A developer can run:

```bash
signal README.md
```

and immediately receive a useful result.

### Explainability

The output must contain more than an AI score.

It should expose the signals contributing to the result:

```text
AI likelihood: 87%
Confidence: High

Signals:
- ...
- ...
- ...
```

### Automation

JSON output must allow Signal to be integrated into other tools:

```bash
signal README.md --json
```

### Architecture

The CLI must not contain analysis logic that prevents reuse by the future API.

The analysis engine must be independently callable.

---

## 19. Long-Term Direction

Signal should become a platform for analyzing content in the AI era rather than simply an "AI detector."

The initial product is:

```text
Signal CLI
```

followed by:

```text
Signal API
```

and then:

```text
Signal MCP
Signal Browser Extension
Signal GitHub Action
Signal SDK
```

The long-term architecture is:

```text
                   ┌─────────────┐
                   │   Signal    │
                   │  Analysis   │
                   │   Engine    │
                   └──────┬──────┘
                          │
                     Signal API
                          │
       ┌──────────────────┼──────────────────┐
       │                  │                  │
     CLI                 MCP              Browser
       │                  │                  │
  Developers          AI Agents           Users
```

The core product value is:

> **Make the signals behind AI-generated content visible.**
