# Signal Analysis Engine — Technical Design

## 1. Purpose

This document defines the technical design of the Signal analysis engine for the MVP.

The engine is responsible for analyzing text content and producing a structured assessment of AI-generation likelihood. It is intentionally designed as an independent core so that the same implementation can be reused by the CLI in the MVP and by a future API without duplicating logic.

This document focuses on:

- Engine responsibilities
- Core domain model
- Detection strategy
- Analysis pipeline
- Component design
- Scoring and confidence design
- Determinism, privacy, and testing requirements
- Extensibility for future versions

This document does not define CLI flags or user-facing command behavior except where the engine contract affects them.

---

## 2. Design Goals

The engine design must satisfy the following goals:

1. Keep analysis logic independent from delivery interfaces such as CLI and API.
2. Treat Signal as an orchestrator of multiple detectors and analyzers rather than a single detector.
3. Produce explainable results rather than a black-box score only.
4. Combine multiple independent signals instead of relying on a single heuristic.
5. Allow both model-based and heuristic signals behind the same result contract.
6. Prefer deterministic, locally computable analysis in the MVP.
7. Leave room for stronger local pretrained models when they provide practical value.
8. Support English and Japanese text without hard-coding English-only assumptions.
9. Preserve privacy by avoiding persistence or external transmission of analyzed content by default.
10. Keep optional LLM-based explanation separate from the core detection path.

---

## 3. Non-Goals

The MVP engine does not aim to:

- Prove whether content is AI-generated
- Support image, audio, or video inputs
- Depend on remote LLM calls during core detection
- Continuously learn from user submissions at runtime
- Provide per-model attribution such as "generated by model X"
- Optimize for every language before the architecture is validated

---

## 4. Architectural Position

The analysis engine is the core domain component of Signal.

Signal should be designed as a collection of detectors and analyzers whose outputs are normalized into a common signal model and then aggregated.

Conceptually:

```text
Input Adapter
  -> Document Builder
  -> Preprocessor
  -> Detector/Analyzer Runners
  -> Score Aggregator
  -> Confidence Estimator
  -> Classification Mapper
  -> AnalysisResult
```

More concretely:

```text
                    Input
                      │
                      ▼
              ┌──────────────┐
              │ Preprocessor │
              └──────┬───────┘
                     │
        ┌────────────┼────────────┐
        │            │            │
        ▼            ▼            ▼
   AI Detector   Statistical   Linguistic
      Model        Signals       Signals
        │            │            │
        └────────────┼────────────┘
                     ▼
              Signal Aggregator
                     │
                     ▼
              Analysis Result
```

In the MVP:

```text
                 ┌────────────────────────┐
                 │ Signal Analysis Engine │
                 └────────────┬───────────┘
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
     Input Contract      Result Contract     Config Contract
          │                   │                   │
          └───────────────────┴───────────────────┘
                              │
                    Thin Interface Adapters
                              │
                   CLI now / API in the future
```

The interface layer may read files, read stdin, print tables, emit JSON, and determine process exit codes. The engine must not depend on any of those concerns.

---

## 5. Responsibilities and Boundaries

### 5.1 Engine Responsibilities

The engine must:

- Accept normalized text input and analysis options
- Build an internal document representation
- Run multiple detector and analyzer components over the same input
- Extract measurable characteristics from the document when needed by heuristic analyzers
- Convert heterogeneous outputs into explainable signals
- Aggregate signals into an overall AI-likelihood score
- Estimate confidence independently from score
- Map score to a classification label
- Return a stable, language-independent result object

### 5.2 Interface Responsibilities

The CLI or future API may:

- Read files or stdin
- Validate command-line arguments
- Format output for humans
- Serialize the engine result to JSON
- Translate engine errors into interface-specific error messages

### 5.3 Explicit Boundary Rule

No scoring, threshold mapping, or signal-generation logic may live in the CLI layer.

## 6. Detection Strategy

There are several major families of AI-generation detection methods. Signal should explicitly model them as different signal sources rather than collapsing everything into one algorithm.

### 6.1 Detection Families

The architecture should support four categories:

1. Dedicated AI-detection models
2. Statistical language-model signals such as perplexity
3. Linguistic and stylistic feature analyzers
4. Optional LLM-based explanation

### 6.2 Dedicated AI-Detection Models

A pretrained AI-generated text detection model is a strong candidate for one of the earliest high-value signals.

Conceptually:

```text
Input text
  -> pretrained detector
  -> AI-likelihood score
  -> DetectorModelSignal
```

This should be treated as one signal source inside Signal, not as the entire product.

Benefits:

- Fast path to a practical baseline
- Easy to explain as one contributing source
- Can provide strong evidence when combined with independent signals

Constraints:

- Model provenance and version must be exposed in engine metadata
- The detector output must be normalized into the common signal format
- The engine must tolerate the detector being disabled or unavailable

### 6.3 Statistical Signals

Statistical signals examine properties such as predictability, repetition, and token distribution.

The most important example is perplexity.

Perplexity should not be treated as a final AI verdict. It should be represented as a signal such as `perplexity_pattern` or a closely named stable type.

Conceptually:

```text
Input text
  -> language model scoring
  -> perplexity or related metric
  -> PerplexitySignal
```

This matters because low perplexity can occur in polished human text, and edited AI text may no longer look trivially predictable.

### 6.4 Linguistic and Stylistic Signals

These are the feature-based analyzers already described elsewhere in this document, such as:

- sentence-length variation
- vocabulary diversity
- phrase repetition
- stylistic variation
- formatting regularity

These analyzers do not directly declare that text is AI-generated. They identify patterns that become more useful when combined with independent model-based or statistical evidence.

### 6.5 LLM-Based Explanation

LLM-as-a-judge should not be the primary detection mechanism in the MVP.

It is more appropriate as a future explanation layer:

```text
Detection
  -> Signals
  -> LLM explainer
  -> Human-readable narrative
```

This keeps the core engine deterministic while still leaving room for richer explanations later.

## 7. Core Domain Model

The engine should use explicit internal models so that analysis steps remain testable and composable.

### 7.1 Document

`Document` is the normalized representation of the input text.

Suggested fields:

```text
Document
- raw_text
- normalized_text
- language_hints
- character_count
- line_count
- paragraph_count
- sentence_units
- token_units
- metadata
```

Notes:

- `raw_text` preserves the original input as received by the engine.
- `normalized_text` is used for deterministic analysis after normalization rules are applied.
- `sentence_units` and `token_units` abstract over language-specific segmentation.
- `metadata` may contain non-sensitive derived information such as normalization version.

### 7.2 Feature Set

`FeatureSet` is an immutable collection of measurable values derived from the document.

Examples:

- Sentence length distribution
- Paragraph length distribution
- Repeated n-gram counts
- Type-token ratio
- Unique phrase ratio
- Punctuation distribution
- Heading/list/code-block ratios for Markdown
- Character-class ratios
- Transition variance between adjacent sentences

Feature extraction should happen before heuristic-analyzer execution so multiple analyzers can reuse the same measurements.

Model-based detectors may bypass much of this layer and emit normalized signals directly.

### 7.3 Signal

`Signal` is the primary explainability unit.

Suggested shape:

```text
Signal
- type
- source_family
- source_name
- score
- weight
- description
- evidence
```

Definitions:

- `type`: stable identifier such as `repetitive_structure`
- `source_family`: one of `detector_model`, `statistical`, `linguistic`, or future categories
- `source_name`: stable component identifier such as `roberta_detector` or `perplexity`
- `score`: normalized analyzer output in the range `0.0..1.0`
- `weight`: optional configured contribution used by the scorer
- `description`: human-readable explanation
- `evidence`: structured derived metrics that justify the signal

The `evidence` field should remain machine-readable so future APIs can expose more detailed inspection views.

This model allows Signal to unify very different signal producers behind one contract.

### 7.4 Analysis Result

`AnalysisResult` is the engine output contract.

Suggested shape:

```text
AnalysisResult
- score
- confidence
- classification
- signals
- input_stats
- engine_info
```

Where:

- `score` is AI-likelihood, not proof
- `confidence` is the reliability of the analysis
- `classification` is derived from configured thresholds
- `signals` is an ordered list of contributing signals
- `input_stats` contains counts required by upstream interfaces
- `engine_info` contains engine version, scoring profile, and enabled component identifiers

## 8. Analysis Pipeline

The engine pipeline should be deterministic and explicit.

### 8.1 Step 1: Input Normalization

Normalization converts raw text into a consistent form for analysis.

The MVP normalization stage should:

- Normalize line endings
- Trim irrelevant leading and trailing whitespace
- Canonicalize repeated blank-line handling
- Preserve semantically meaningful punctuation
- Preserve case unless a specific feature extractor explicitly uses case-folded text
- Preserve Markdown structure when possible

Normalization must be versioned because even small changes can alter analysis output.

### 8.2 Step 2: Language-Aware Segmentation

The engine should segment the document into analyzable units.

Required units:

- Characters
- Lines
- Paragraphs
- Sentence-like units
- Token-like units

The design must not assume whitespace-separated words. For Japanese, tokenization may rely on a dedicated tokenizer or a documented fallback strategy. The exact tokenizer is an implementation choice, but the abstraction must remain hidden behind the document-building layer.

### 8.3 Step 3: Shared Preparation

After preprocessing, the engine should prepare whatever shared artifacts are needed by enabled components.

This may include:

- tokenization outputs
- sentence segmentation
- feature extraction for heuristic analyzers
- tensor or model inputs for local detector models
- normalized text views for perplexity scoring

The important design rule is that preparation remains a reusable engine concern rather than being duplicated inside each interface.

### 8.4 Step 4: Detector and Analyzer Execution

The engine should execute a set of enabled components, each producing zero or more normalized signals.

Two broad component styles are expected:

- Direct detectors that map input to an AI-likelihood-like signal
- Heuristic analyzers that map features to narrower evidence signals

Conceptual interface:

```text
Component.run(document, prepared_inputs) -> []Signal
```

Examples:

- `DetectorModelComponent`
- `PerplexityComponent`
- `SentenceStructureAnalyzer`
- `VocabularyPatternAnalyzer`

Each component should:

- Be deterministic
- Expose stable component metadata
- Normalize its result into the shared signal contract
- Return no signal when evidence is insufficient
- Expose enough evidence for debugging and future inspection

### 8.5 Step 5: Score Aggregation

The scorer combines signal outputs into a single AI-likelihood score.

The aggregation layer must:

- Use configuration rather than hard-coded weights where possible
- Handle missing signals gracefully
- Normalize the final score to `0.0..1.0`
- Remain explainable and inspectable

The aggregator should be designed around the idea that different signal families provide partially independent evidence.

At minimum, the scorer should be able to combine:

- dedicated detector-model output
- perplexity or statistical output
- multiple linguistic feature signals

This makes the final result more defensible than any single signal alone.

### 8.6 Step 6: Confidence Estimation

Confidence is computed independently from score.

Confidence should account for:

- Input length sufficiency
- Number of components that produced usable evidence
- Diversity of signal families represented in the result
- Agreement or disagreement between signals
- Coverage of applicable features
- Known limitations for the detected input profile

High score with low confidence must be possible.

### 8.7 Step 7: Classification Mapping

Classification is a post-processing step that maps score ranges to labels.

Initial labels:

```text
likely_human
possibly_human
uncertain
possibly_ai_generated
likely_ai_generated
```

Thresholds must live in configuration and be validated against the evaluation dataset.

## 9. Component Design

Signal should use a generalized component model so detector models and heuristic analyzers can coexist cleanly.

### 9.1 Component Types

Recommended component categories:

- `DetectorComponent`
- `StatisticalComponent`
- `AnalyzerComponent`
- future `ExplainerComponent`

All of them should emit the same `Signal` structure.

### 9.2 Design Principles

Each component should satisfy these rules:

1. It measures a specific hypothesis or evidence source.
2. Its output is explainable in plain language.
3. Its scoring function is bounded and deterministic unless explicitly documented otherwise.
4. It degrades safely on short, malformed, or multilingual input.
5. It can be unit-tested independently.
6. It declares its source family and version metadata.

### 9.3 Initial MVP Components

The MVP should begin with a small set of components that can be implemented locally and explained clearly.

Recommended initial mix:

- One dedicated detector-model component if a suitable local pretrained model is validated
- One perplexity or related statistical component if operationally practical
- Several linguistic analyzers:
  - Structure analyzer
  - Repetition analyzer
  - Vocabulary analyzer
  - Style-variation analyzer
  - Formatting-pattern analyzer

### 9.4 Candidate MVP Signals

The exact implemented set can change, but the engine should be designed around signals such as:

- `detector_model_score`
- `perplexity_pattern`
- `repetitive_structure`
- `sentence_length_consistency`
- `phrase_repetition`
- `low_vocabulary_diversity`
- `low_stylistic_variation`
- `template_like_formatting`

These signals should be treated as examples of measurable patterns, not claims of causation on their own.

### 9.5 Component Registration

Components should be instantiated through a registry or explicit composition root.

This provides:

- Clear control over enabled components
- Easy experimentation with component mixes
- Stable ordering for deterministic output
- Future support for analysis profiles

### 9.6 Signal Ordering

Returned signals should be sorted deterministically, preferably by descending contribution and then by stable type name.

This matters for:

- Human-readable output consistency
- JSON contract stability
- Golden tests

## 10. Scoring Design

### 10.1 Scoring Philosophy

The scorer should combine evidence without pretending to be mathematically stronger than it is.

For the MVP, the goal is:

- Stable behavior
- Explainability
- Easy calibration
- Support for iteration against a labeled evaluation set

### 10.2 Recommended MVP Approach

A weighted aggregation scorer is the most practical starting point.

Conceptually:

```text
final_score = normalize(sum(signal.score * signal.weight))
```

This approach is appropriate for the MVP because it is:

- Easy to inspect
- Easy to tune
- Easy to version
- Compatible with deterministic local execution

The weighting scheme should explicitly account for the fact that a dedicated detector model, perplexity, and linguistic signals are not identical kinds of evidence.

### 10.3 Calibration

The engine should leave room for later statistical calibration.

Future options may include:

- Threshold tuning
- Platt scaling
- Isotonic calibration
- Replacement with a trained meta-classifier

The public result contract should not need to change if the internals evolve.

### 10.4 Score Versioning

The engine should expose a scoring profile or engine version in the result metadata so evaluation results remain comparable over time.

---

## 11. Confidence Design

Confidence must not be a mirror of score.

### 11.1 Proposed Inputs to Confidence

Confidence estimation may use:

- Minimum input-size gates
- Number of components that ran successfully
- Number of components that produced meaningful output
- Variance across signal scores
- Presence of conflicting evidence
- Language-support certainty

### 11.2 Confidence Levels

The MVP should keep:

```text
low
medium
high
```

Mapping logic should be explicit and testable.

Example reasoning:

- `low`: input too short, poor segmentation quality, or sparse signal evidence
- `medium`: sufficient input with partial component agreement
- `high`: sufficient input with broad, coherent evidence across components

---

## 12. Configuration Design

The engine should allow controlled tuning without code changes to the interface layer.

Configurable items may include:

- Enabled components
- Per-signal weights
- Classification thresholds
- Minimum input lengths
- Language-specific tokenizer behavior
- Detector-model selection and local model paths
- Perplexity-model selection
- Feature-extraction limits for performance protection

Configuration must be versioned together with the engine release or analysis profile.

For the MVP, configuration may be static and compiled in, as long as the design does not force those values into the CLI layer.

---

## 13. Error Handling

The engine should return domain-relevant errors and avoid interface-specific presentation details.

Examples:

- Empty input
- Invalid UTF-8 after decoding boundary assumptions
- Unsupported analysis option
- Internal segmentation failure
- Inconsistent configuration

The engine must not include raw sensitive content in error values unless explicitly required for debugging and kept out of default interface output.

---

## 14. Determinism and Reproducibility

Determinism is a core MVP requirement.

For the same:

- Input text
- Normalization rules
- Enabled components
- Configuration
- Engine version

the engine should produce the same result.

To support reproducibility:

- Component ordering must be fixed
- Floating-point handling should be consistent
- Randomness must not be used in the MVP core path
- Version metadata should identify engine and scoring revisions

If future versions introduce non-deterministic models, the engine contract must expose enough metadata to explain that behavior.

---

## 15. Performance Considerations

The MVP is a local CLI-first system, so startup cost and predictable runtime matter.

### 15.1 Performance Principles

- Compute shared features once
- Avoid repeated tokenization work
- Keep memory proportional to input size
- Use linear or near-linear algorithms where practical
- Bound expensive operations on extremely large inputs

### 15.2 Practical Limits

The engine may define safety limits such as:

- Maximum input characters
- Maximum repeated-pattern search window
- Maximum stored evidence items per signal

These limits should fail gracefully or degrade analysis detail rather than crash the process.

---

## 16. Privacy and Data Handling

The engine must assume analyzed content may be sensitive.

Therefore, the MVP engine must:

- Operate locally by default
- Avoid persistence of input content
- Avoid logging raw analyzed text
- Avoid remote calls during analysis unless explicitly introduced and documented
- Keep result evidence derived and minimal

If future components require external models or services, that must be an opt-in architectural change with explicit documentation.

---

## 17. Testing Strategy

The engine should be testable at multiple layers.

### 17.1 Unit Tests

Unit-test each of the following independently:

- Normalization
- Segmentation
- Feature extraction
- Individual components
- Score aggregation
- Confidence mapping
- Classification mapping

### 17.2 Contract Tests

Contract tests should validate that `AnalysisResult` remains schema-stable for downstream consumers.

### 17.3 Golden Tests

Representative fixtures should verify deterministic end-to-end output for:

- Human-written prose
- AI-generated prose
- Human-edited AI text
- Mixed text
- Markdown-heavy content
- Japanese text

### 17.4 Evaluation Tests

The engine must be evaluated against a versioned dataset so score changes can be measured across releases.

The evaluation process should track:

- Precision and recall by threshold
- False-positive and false-negative patterns
- Confidence distribution
- Language-specific behavior
- Regression against prior engine versions

---

## 18. Extensibility

The design should support future growth without rewriting the core.

Expected extension points:

- New detector models
- New statistical components
- New analyzers
- New signal types
- Language-specific segmentation strategies
- Alternative scoring strategies
- Optional LLM-based explanation
- API exposure of structured evidence
- Analysis profiles for different content types such as code, essays, or Markdown-heavy documents

The engine contract should remain stable even if the internal implementation shifts from heuristic aggregation to a trained ensemble.

## 19. Recommended Implementation Shape

The exact directory layout depends on language choice, but the design should map cleanly to components such as:

```text
internal/
  engine/
    engine.*
  document/
    builder.*
    normalize.*
    segment.*
  features/
    extractor.*
    structure.*
    repetition.*
    vocabulary.*
    style.*
  analyzers/
    analyzer.*
    structure.*
    repetition.*
    vocabulary.*
    style.*
    formatting.*
  detectors/
    detector.*
    model.*
    perplexity.*
  scoring/
    scorer.*
    confidence.*
    classification.*
  model/
    document.*
    signal.*
    result.*
  config/
    profile.*
```

This shape is intended to preserve domain boundaries, not to prescribe language-specific package names.

## 20. Open Technical Decisions

The following items should be resolved during implementation planning:

1. Which tokenizer or segmentation strategy should be used for Japanese in the MVP.
2. Which existing local pretrained detector model should be evaluated first.
3. Whether perplexity is operationally practical in the MVP and which local model should provide it.
4. Which signal definitions are reliable enough to ship initially.
5. Whether Markdown structure should be analyzed as plain text only or with lightweight structural awareness.
6. How much signal evidence should be exposed in JSON without making the output noisy or unstable.
7. What minimum input size should cap confidence at `low`.

These decisions should be documented together with the first concrete implementation.

---

## 21. Summary

The Signal analysis engine should be a deterministic, explainable, interface-independent core that aggregates multiple kinds of evidence into:

- AI-likelihood score
- Confidence level
- Classification
- Contributing signals
- Stable structured metadata

The core design should treat Signal not as a single detector, but as a system that combines:

- dedicated AI-detection model output
- statistical evidence such as perplexity
- linguistic and stylistic analyzers
- optional future LLM-based explanation

The MVP should favor a small number of strong, explainable components over premature complexity. If the engine boundary remains clean, Signal can evolve from a CLI-first tool into an API-centered analysis platform without rewriting its core detection logic.
