# Signal Analysis Engine — Technical Design

## 1. Purpose

This document defines the technical design of the Signal analysis engine for the MVP.

The engine is responsible for analyzing text content and producing a structured assessment of AI-generation likelihood. It is intentionally designed as an independent core so that the same implementation can be reused by the CLI in the MVP and by a future API without duplicating logic.

This document focuses on:

- Engine responsibilities
- Core domain model
- Analysis pipeline
- Signal-analyzer design
- Scoring and confidence design
- Determinism, privacy, and testing requirements
- Extensibility for future versions

This document does not define CLI flags or user-facing command behavior except where the engine contract affects them.

---

## 2. Design Goals

The engine design must satisfy the following goals:

1. Keep analysis logic independent from delivery interfaces such as CLI and API.
2. Produce explainable results rather than a black-box score only.
3. Combine multiple independent signals instead of relying on a single heuristic.
4. Prefer deterministic, locally computable analysis in the MVP.
5. Make it easy to add, remove, or tune analyzers without changing the public result contract.
6. Support English and Japanese text without hard-coding English-only assumptions.
7. Preserve privacy by avoiding persistence or external transmission of analyzed content by default.

---

## 3. Non-Goals

The MVP engine does not aim to:

- Prove whether content is AI-generated
- Support image, audio, or video inputs
- Depend on remote LLM calls during core analysis
- Continuously learn from user submissions at runtime
- Provide per-model attribution such as "generated by model X"
- Optimize for every language before the architecture is validated

---

## 4. Architectural Position

The analysis engine is the core domain component of Signal.

Conceptually:

```text
Input Adapter
  -> Document Builder
  -> Preprocessor
  -> Feature Extractors
  -> Signal Analyzers
  -> Score Aggregator
  -> Confidence Estimator
  -> Classification Mapper
  -> AnalysisResult
```

In the MVP:

```text
                 ┌────────────────────────┐
                 │ Signal Analysis Engine │
                 └────────────┬───────────┘
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
     Input Contract      Result Contract     Config Contract
          │                   │                   │
          └───────────────────┴───────────────────┘
                              │
                    Thin Interface Adapters
                              │
                   CLI now / API in the future
```

The interface layer may read files, read stdin, print tables, emit JSON, and determine process exit codes. The engine must not depend on any of those concerns.

---

## 5. Responsibilities and Boundaries

### 5.1 Engine Responsibilities

The engine must:

- Accept normalized text input and analysis options
- Build an internal document representation
- Extract measurable characteristics from the document
- Run analyzers that convert features into explainable signals
- Aggregate signals into an overall AI-likelihood score
- Estimate confidence independently from score
- Map score to a classification label
- Return a stable, language-independent result object

### 5.2 Interface Responsibilities

The CLI or future API may:

- Read files or stdin
- Validate command-line arguments
- Format output for humans
- Serialize the engine result to JSON
- Translate engine errors into interface-specific error messages

### 5.3 Explicit Boundary Rule

No scoring, threshold mapping, or signal-generation logic may live in the CLI layer.

---

## 6. Core Domain Model

The engine should use explicit internal models so that analysis steps remain testable and composable.

### 6.1 Document

`Document` is the normalized representation of the input text.

Suggested fields:

```text
Document
- raw_text
- normalized_text
- language_hints
- character_count
- line_count
- paragraph_count
- sentence_units
- token_units
- metadata
```

Notes:

- `raw_text` preserves the original input as received by the engine.
- `normalized_text` is used for deterministic analysis after normalization rules are applied.
- `sentence_units` and `token_units` abstract over language-specific segmentation.
- `metadata` may contain non-sensitive derived information such as normalization version.

### 6.2 Feature Set

`FeatureSet` is an immutable collection of measurable values derived from the document.

Examples:

- Sentence length distribution
- Paragraph length distribution
- Repeated n-gram counts
- Type-token ratio
- Unique phrase ratio
- Punctuation distribution
- Heading/list/code-block ratios for Markdown
- Character-class ratios
- Transition variance between adjacent sentences

Feature extraction should happen before analyzer execution so multiple analyzers can reuse the same measurements.

### 6.3 Signal

`Signal` is the primary explainability unit.

Suggested shape:

```text
Signal
- type
- score
- weight
- description
- evidence
```

Definitions:

- `type`: stable identifier such as `repetitive_structure`
- `score`: normalized analyzer output in the range `0.0..1.0`
- `weight`: optional configured contribution used by the scorer
- `description`: human-readable explanation
- `evidence`: structured derived metrics that justify the signal

The `evidence` field should remain machine-readable so future APIs can expose more detailed inspection views.

### 6.4 Analysis Result

`AnalysisResult` is the engine output contract.

Suggested shape:

```text
AnalysisResult
- score
- confidence
- classification
- signals
- input_stats
- engine_info
```

Where:

- `score` is AI-likelihood, not proof
- `confidence` is the reliability of the analysis
- `classification` is derived from configured thresholds
- `signals` is an ordered list of contributing signals
- `input_stats` contains counts required by upstream interfaces
- `engine_info` contains engine version and analysis profile identifiers

## 7. Analysis Pipeline

The engine pipeline should be deterministic and explicit.

### 7.1 Step 1: Input Normalization

Normalization converts raw text into a consistent form for analysis.

The MVP normalization stage should:

- Normalize line endings
- Trim irrelevant leading and trailing whitespace
- Canonicalize repeated blank-line handling
- Preserve semantically meaningful punctuation
- Preserve case unless a specific feature extractor explicitly uses case-folded text
- Preserve Markdown structure when possible

Normalization must be versioned because even small changes can alter analysis output.

### 7.2 Step 2: Language-Aware Segmentation

The engine should segment the document into analyzable units.

Required units:

- Characters
- Lines
- Paragraphs
- Sentence-like units
- Token-like units

The design must not assume whitespace-separated words. For Japanese, tokenization may rely on a dedicated tokenizer or a documented fallback strategy. The exact tokenizer is an implementation choice, but the abstraction must remain hidden behind the document-building layer.

### 7.3 Step 3: Feature Extraction

Feature extraction computes reusable document metrics once.

This layer should:

- Be deterministic
- Avoid duplication across analyzers
- Expose typed values instead of ad hoc maps where practical
- Tolerate short or noisy inputs

Example categories:

- Structural features
- Lexical features
- Repetition features
- Stylistic features
- Formatting features

### 7.4 Step 4: Signal Analysis

Each analyzer examines the document and feature set, then returns zero or more signals.

Conceptual interface:

```text
Analyzer.analyze(document, features) -> []Signal
```

An analyzer should:

- Focus on one coherent phenomenon
- Produce stable output for the same input
- Return no signal when evidence is insufficient
- Expose enough evidence for debugging and future inspection

### 7.5 Step 5: Score Aggregation

The scorer combines signal outputs into a single AI-likelihood score.

The aggregation layer must:

- Use configuration rather than hard-coded weights where possible
- Handle missing signals gracefully
- Normalize the final score to `0.0..1.0`
- Remain explainable and inspectable

### 7.6 Step 6: Confidence Estimation

Confidence is computed independently from score.

Confidence should account for:

- Input length sufficiency
- Number of analyzers that produced usable evidence
- Agreement or disagreement between signals
- Coverage of applicable features
- Known limitations for the detected input profile

High score with low confidence must be possible.

### 7.7 Step 7: Classification Mapping

Classification is a post-processing step that maps score ranges to labels.

Initial labels:

```text
likely_human
possibly_human
uncertain
possibly_ai_generated
likely_ai_generated
```

Thresholds must live in configuration and be validated against the evaluation dataset.

## 8. Analyzer Design

### 8.1 Analyzer Principles

Each analyzer should satisfy these rules:

1. It measures a specific hypothesis.
2. Its output is explainable in plain language.
3. Its scoring function is bounded and deterministic.
4. It degrades safely on short, malformed, or multilingual input.
5. It can be unit-tested independently.

### 8.2 Initial Analyzer Families

The MVP should begin with a small set of analyzers that can be implemented locally and explained clearly.

Recommended families:

- Structure analyzer
- Repetition analyzer
- Vocabulary analyzer
- Style-variation analyzer
- Formatting-pattern analyzer

### 8.3 Candidate MVP Signals

The exact implemented set can change, but the engine should be designed around signals such as:

- `repetitive_structure`
- `sentence_length_consistency`
- `phrase_repetition`
- `low_vocabulary_diversity`
- `low_stylistic_variation`
- `template_like_formatting`

These signals should be treated as examples of measurable patterns, not claims of causation on their own.

### 8.4 Analyzer Registration

Analyzers should be instantiated through a registry or explicit composition root.

This provides:

- Clear control over enabled analyzers
- Easy experimentation with analyzer sets
- Stable ordering for deterministic output
- Future support for analysis profiles

### 8.5 Signal Ordering

Returned signals should be sorted deterministically, preferably by descending contribution and then by stable type name.

This matters for:

- Human-readable output consistency
- JSON contract stability
- Golden tests

## 9. Scoring Design

### 9.1 Scoring Philosophy

The scorer should combine evidence without pretending to be mathematically stronger than it is.

For the MVP, the goal is:

- Stable behavior
- Explainability
- Easy calibration
- Support for iteration against a labeled evaluation set

### 9.2 Recommended MVP Approach

A weighted heuristic scorer is the most practical starting point.

Conceptually:

```text
final_score = normalize(sum(signal.score * signal.weight))
```

This approach is appropriate for the MVP because it is:

- Easy to inspect
- Easy to tune
- Easy to version
- Compatible with deterministic local execution

### 9.3 Calibration

The engine should leave room for later statistical calibration.

Future options may include:

- Threshold tuning
- Platt scaling
- Isotonic calibration
- Replacement with a trained meta-classifier

The public result contract should not need to change if the internals evolve.

### 9.4 Score Versioning

The engine should expose a scoring profile or engine version in the result metadata so evaluation results remain comparable over time.

---

## 10. Confidence Design

Confidence must not be a mirror of score.

### 10.1 Proposed Inputs to Confidence

Confidence estimation may use:

- Minimum input-size gates
- Number of analyzers that ran successfully
- Number of analyzers that produced meaningful output
- Variance across signal scores
- Presence of conflicting evidence
- Language-support certainty

### 10.2 Confidence Levels

The MVP should keep:

```text
low
medium
high
```

Mapping logic should be explicit and testable.

Example reasoning:

- `low`: input too short, poor segmentation quality, or sparse signal evidence
- `medium`: sufficient input with partial analyzer agreement
- `high`: sufficient input with broad, coherent evidence across analyzers

---

## 11. Configuration Design

The engine should allow controlled tuning without code changes to the interface layer.

Configurable items may include:

- Enabled analyzers
- Per-signal weights
- Classification thresholds
- Minimum input lengths
- Language-specific tokenizer behavior
- Feature-extraction limits for performance protection

Configuration must be versioned together with the engine release or analysis profile.

For the MVP, configuration may be static and compiled in, as long as the design does not force those values into the CLI layer.

---

## 12. Error Handling

The engine should return domain-relevant errors and avoid interface-specific presentation details.

Examples:

- Empty input
- Invalid UTF-8 after decoding boundary assumptions
- Unsupported analysis option
- Internal segmentation failure
- Inconsistent configuration

The engine must not include raw sensitive content in error values unless explicitly required for debugging and kept out of default interface output.

---

## 13. Determinism and Reproducibility

Determinism is a core MVP requirement.

For the same:

- Input text
- Normalization rules
- Analyzer set
- Configuration
- Engine version

the engine should produce the same result.

To support reproducibility:

- Analyzer ordering must be fixed
- Floating-point handling should be consistent
- Randomness must not be used in the MVP
- Version metadata should identify engine/scoring revisions

If future versions introduce non-deterministic models, the engine contract must expose enough metadata to explain that behavior.

---

## 14. Performance Considerations

The MVP is a local CLI-first system, so startup cost and predictable runtime matter.

### 14.1 Performance Principles

- Compute shared features once
- Avoid repeated tokenization work
- Keep memory proportional to input size
- Use linear or near-linear algorithms where practical
- Bound expensive operations on extremely large inputs

### 14.2 Practical Limits

The engine may define safety limits such as:

- Maximum input characters
- Maximum repeated-pattern search window
- Maximum stored evidence items per signal

These limits should fail gracefully or degrade analysis detail rather than crash the process.

---

## 15. Privacy and Data Handling

The engine must assume analyzed content may be sensitive.

Therefore, the MVP engine must:

- Operate locally by default
- Avoid persistence of input content
- Avoid logging raw analyzed text
- Avoid remote calls during analysis unless explicitly introduced and documented
- Keep result evidence derived and minimal

If future analyzers require external models or services, that must be an opt-in architectural change with explicit documentation.

---

## 16. Testing Strategy

The engine should be testable at multiple layers.

### 16.1 Unit Tests

Unit-test each of the following independently:

- Normalization
- Segmentation
- Feature extraction
- Individual analyzers
- Score aggregation
- Confidence mapping
- Classification mapping

### 16.2 Contract Tests

Contract tests should validate that `AnalysisResult` remains schema-stable for downstream consumers.

### 16.3 Golden Tests

Representative fixtures should verify deterministic end-to-end output for:

- Human-written prose
- AI-generated prose
- Human-edited AI text
- Mixed text
- Markdown-heavy content
- Japanese text

### 16.4 Evaluation Tests

The engine must be evaluated against a versioned dataset so score changes can be measured across releases.

The evaluation process should track:

- Precision and recall by threshold
- False-positive and false-negative patterns
- Confidence distribution
- Language-specific behavior
- Regression against prior engine versions

---

## 17. Extensibility

The design should support future growth without rewriting the core.

Expected extension points:

- New analyzers
- New signal types
- Language-specific segmentation strategies
- Alternative scoring strategies
- API exposure of structured evidence
- Analysis profiles for different content types such as code, essays, or Markdown-heavy documents

The engine contract should remain stable even if the internal implementation shifts from heuristic aggregation to a trained ensemble.

---

## 18. Recommended Implementation Shape

The exact directory layout depends on language choice, but the design should map cleanly to components such as:

```text
internal/
  engine/
    engine.*
  document/
    builder.*
    normalize.*
    segment.*
  features/
    extractor.*
    structure.*
    repetition.*
    vocabulary.*
    style.*
  analyzers/
    analyzer.*
    structure.*
    repetition.*
    vocabulary.*
    style.*
    formatting.*
  scoring/
    scorer.*
    confidence.*
    classification.*
  model/
    document.*
    signal.*
    result.*
  config/
    profile.*
```

This shape is intended to preserve domain boundaries, not to prescribe language-specific package names.

---

## 19. Open Technical Decisions

The following items should be resolved during implementation planning:

1. Which tokenizer or segmentation strategy should be used for Japanese in the MVP.
2. Which signal definitions are reliable enough to ship initially.
3. Whether Markdown structure should be analyzed as plain text only or with lightweight structural awareness.
4. How much signal evidence should be exposed in JSON without making the output noisy or unstable.
5. What minimum input size should cap confidence at `low`.

These decisions should be documented together with the first concrete implementation.

---

## 20. Summary

The Signal analysis engine should be a deterministic, explainable, interface-independent core that transforms text into:

- AI-likelihood score
- Confidence level
- Classification
- Contributing signals
- Stable structured metadata

The MVP should favor a small number of strong, explainable analyzers over premature complexity. If the engine boundary remains clean, Signal can evolve from a CLI-first tool into an API-centered analysis platform without rewriting its core detection logic.
